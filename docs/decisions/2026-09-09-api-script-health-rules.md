# API 脚本与健康规则共同执行

状态：接受。日期：2026-09-09。

## Context

二手车 API 探活需要先获取当前车源及签名，用户同时需要可见、可维护的健康判定规则。此前 API 规则会直接替代脚本执行，迫使动态探活把所有验证隐藏在脚本中。

## Evidence

`CheckRunner._run_check_attempt` 优先选择结构化 API 路径；`RunContext` 初始化时解析请求配置；API 字段预览只发单次请求；HTTP 交互历史仅为 UI 保存。线上检查确认项目 1 的 API 无脚本，项目 2 的 15 个 API 仅有脚本且固定在主节点执行，没有同时配置两者的历史任务。

## Decision

由同一 API 执行入口处理脚本与规则：先完成动态请求，再对最后一次响应运行结构化规则，不重复请求。请求配置按调用时变量解析，预览复用动态执行。保留有界、脱敏的请求历史及目标请求与任务整体耗时。继续支持只有规则或只有脚本的任务，不新增数据库字段。

## Alternatives considered

- 仅补脚本注释：不能解决规则不可见，也不能修复编辑器优先级陷阱。
- 脚本后重新请求 URL：可能重复调用接口，且丢失脚本实际生成的 Headers、签名和参数。
- 新增 API 页面式 setup_script 或工作流引擎：增加不必要的入口和配置迁移。

## Consequences

同时存在脚本和规则时语义发生变化，升级前必须检查历史任务和执行节点。当前 15 项仅由主节点执行，原规则任务与原纯脚本任务保持原有入口。代码和数据库分别备份；回退需还原旧应用和受影响任务配置，不能将新混合配置交给旧执行器。

## Verification

验证包括真实隔离 HTTP 的动态变量、最终响应规则、依赖失败、规则失败、超时、脱敏和预览一致性；前端构建、浏览器编辑/预览/试运行；线上 15 项逐项调试、正式运行和定时调度。实际结果记录在本次交付报告。

## Revisit when

需要跨请求业务断言或正式接口自动化时另行设计；当前功能只负责一次探活的依赖准备和最终响应健康判定。
