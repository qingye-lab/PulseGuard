# 历史分页精确总数

- Status: Accepted
- Date: 2026-10-22
- Scope: SQLite 运行记录分页及发布快照冻结边界

## Context

用户观察到 `runs-page?observation_kind=observation&page=1&page_size=12` 耗时 23.57 秒。服务健康端点正常不代表历史分页正常；此前资源治理验收未覆盖大历史量的冷缓存计数。

## Evidence

对应服务端请求耗时 23,544.98 ms，其中 `runs_count=23,323.94 ms`、`runs_fetch=189.09 ms`，项目匹配 811,300 条记录。另有相同接口 41,023.60 ms 的样本，其中计数占 40,822.18 ms。连接、维护门和分发都只有数毫秒，排除了这次主要由客户端排队或 SQLite 写锁造成的假设。

生产计划已使用 `idx_runs_project_kind_started` 覆盖索引；已有索引并未避免精确 COUNT 的线性遍历。暖缓存复测约 70–201 ms，也不能否认冷缓存长尾。降低主机读盘限额后，这类无界扫描的耗时更明显。

## Decision

增加派生表 `run_count_totals`，按 `(project_id, observation_kind)` 保存精确数量，迁移标记为 `schema_versions=4`。首次安装在一个写事务内通过已有窄覆盖索引回填，并安装 INSERT、DELETE、范围字段 UPDATE 触发器。正常重启只检查元数据；缺失派生表或触发器时重建派生计数。原始运行记录是事实源，计数可以再生成。

触发器与原写入一同提交或回滚，适用于独立连接和不同进程。修改状态、通知或大字段不会重写计数。计数为零时移除该维度行。既有写入路径使用 INSERT/UPDATE/DELETE；没有新增任意 SQL 管理工具或 REPLACE 写入契约。

只有项目与运行来源两个维度的普通分页读取该表。筛选解析器生成其他条件时保留原有精确 SQL 统计，避免遗漏条件；总数与页面数据继续共享同一 WAL 读快照。响应字段、顺序、分页大小、项目隔离及准确性均不变。

部署恢复点仍使用 `scripts/deployment_backups.py`。增加可选的 Python `on_snapshot` 回调：源码、运行密钥和 SQLite 不可变副本均已捕获后，调用者可释放写入围栏并恢复原实例，余下完整性检查与压缩校验继续处理冻结文件。回调不是备份完成信号，失败点不能用于发布或标记完成。默认 CLI 和保留规则保持不变；验证 SQLite 缓存显式限制为 64 MiB。

同轮回归以冻结时钟复现了在线备份文件名碰撞。备份文件名原本是调用者不解析的标识，继续保留日期前缀并追加随机 UUID，避免安全副本覆盖恢复源。

## Alternatives considered

不使用近似总数或有时效窗口的内存缓存：它们改变准确性，且不能消除首个请求的冷扫描。不放宽主服务读盘保护来掩盖查询成本。不为这条只需两个维度的接口引入外部数据库或复杂统计立方体。

## Consequences

普通分页统计成本与历史条数解耦。每条记录的增删多一次很小的计数维护；首次回填仍有窄索引扫描成本，须在副本预演并受资源限制。包含状态、全文搜索、时间范围、节点等其他筛选的计数，以及深页 OFFSET，仍可能随历史规模增长，本次没有对其作统一低延迟保证。

数据库变化是附加的派生表和触发器；源代码回退无需恢复或覆盖在线历史，旧代码可继续写入且触发器继续维护计数。若要移除派生结构，应在独立维护操作中进行，不能把回滚代码等同于回滚业务数据。

## Verification

回归覆盖普通分页禁止历史 COUNT、所有项目/来源组合、复杂筛选、独立写入连接、回滚、范围变更、触发器缺失修复、迁移中途失败及读快照一致性。旧分页实现与旧时间文件名实现均在对应回归中失败。生产发布前仍需完成完整恢复点、现有库副本初始化及行数/最大 ID/ID 和、配置指纹和页面内容对比；随后测量真实接口的 `Server-Timing`，不以健康端点代替分页验收。

## Revisit when

其他筛选开始频繁超过一秒、项目/来源维度显著扩展、增加新的原始 SQL 写入方式，或部署改为多实例时重新评估统计所有权与索引策略。
