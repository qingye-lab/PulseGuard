# 控制台分页、状态摘要与慢请求计时

- Status: accepted; deployed to Volcano on 2026-09-14 as perf-0f4712fc512c
- Date: 2026-09-14
- Owners: PulseGuard maintainers
- Scope: SQLite read indexes, status/maintenance reads, console request diagnostics
- Supersedes: none

## Context

火山运行记录分页偶尔出现约 78 秒耗时，多个状态/概览请求超过一秒。当前部署仍为单应用实例，用户同意先修复查询问题；本次不迁移 PostgreSQL。

## Evidence

[只读调查](../reviews/2026-09-14-volcano-api-performance.md)确认项目 2 的精确计数约 1.09 秒，而 12 条摘要读取不到 1 ms；旧计数计划使用项目索引后访问宽行过滤 observation_kind。状态页调用完整概览，重复扫描约 12.8 万条七天历史；Layout 仅需要其中的维护公告。约 78 秒异常未复现，不能据此断言全部长尾来自同一条 COUNT。

## Decision

1. 保留 SQLite、精确总数、`started_at DESC, id DESC` 排序、读事务快照和现有健康统计口径。在既有列迁移完成后添加项目/观测类型/时间索引和项目/健康影响/时间的趋势覆盖索引；不删除既有索引或转换运行数据。
2. 将当前状态摘要提取为共享查询；状态页不再计算概览的趋势、最新恢复等不用的内容。完整概览继续实时计算，暂不引入缓存失效或近似百分位数语义。
3. 新增实例共享 `GET /api/maintenance`，只返回原状态页内维护对象的五个字段，使用相同脱敏函数。Layout 改用该接口；项目状态页的请求头要求和响应结构保持一致。
4. 对固定控制台 GET 路由增加请求 ID、Server-Timing 和 500 ms 慢日志。使用请求上下文隔离同步工作线程，记录维护门、写锁、数据库连接阶段及关键查询；不接收外部请求 ID 或记录请求/SQL 内容。

## Alternatives considered

- 立即迁移 PostgreSQL：成本高，不能自动消除重复计算或应用阻塞；当前先修复已确认的查询路径。
- 缓存分页精确总数或只返回估计值：改变分页实时性或总数口径，不需要作为本轮首选。
- 缓存完整概览：可能有价值，但先测量索引及去重收益，避免先引入跨写入路径的失效逻辑。
- 强制 SQL 使用某个索引或改为分页游标：当前查询计划已使用目标索引，不引入 planner 提示或改变页码契约。

## Consequences

新增两条索引需要一次构建时间与磁盘空间，之后每次运行写入也需要维护索引。在 26 万条合成宽行数据上，初始化并建索引用时 3.55 秒，数据库增加约 26.8 MiB；不能作为火山构建时间或写入代价的保证。精确计数仍随匹配记录数增长，概览仍处理七天样本，持续增长时需要另行评估聚合与保留策略。

线上部署前必须按仓库规则建立应用一致备份，在当前生产库的副本上执行 `storage.init_db()`，验证指纹、完整性、磁盘余量和索引计划，再决定实际发布。用户后续授权部署后，已完成上述预演并于 2026-09-14 发布火山；备份和详细校验见调查文档第 13 节。回退使用原完整应用构建，新增索引兼容旧代码，可保留；无需恢复历史数据。

## Verification

- 隔离临时库完整后端测试 597 项通过；覆盖索引迁移幂等、数据不变、分页/过滤/项目边界、查询计划、状态页不计算趋势、公告脱敏、并发请求计时隔离及错误清理。
- 前端生产构建及现有闭包预算通过。
- 同一 26 万条、约 3.58 GB 合成数据库，本地暖缓存五次采样中位数：分页 161.26 → 23.19 ms，状态页 290.12 → 42.97 ms，概览 284.38 → 132.60 ms；分页响应完全一致，quick_check 为 ok。
- Edge 1440×900 实际渲染公告、概览和运行记录，确认 Layout 请求 maintenance、未请求 status-page，响应包含分段计时，无 console 错误或警告。证据与测量边界见调查文档第 12 节。
- 火山部署后，每项 12 次公网顺序请求中位数：分页第 1/2 页 27.32/27.59 ms、状态页 29.64 ms、概览 267.61 ms、公告 13.91 ms。三轮并发中一次概览端到端 1.93 秒、服务端计时 344 ms，已记录为应用计时区间之外的剩余等待，未将其误判为数据库慢查询。

## Revisit when

- 部署后仍存在一秒以上或数十秒请求，根据对应请求 ID、分段日志与主机指标继续定位。
- 七天样本显著增长、精确计数或趋势仍不能满足延迟目标，评估增量聚合、历史生命周期和缓存。
- 需要多应用实例、高并发写入或一年完整明细在线分析时，重新评估 PostgreSQL 及调度/维护锁的跨进程边界。
