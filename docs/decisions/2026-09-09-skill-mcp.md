# Local stdio MCP and operational Skill

- Status: accepted
- Date: 2026-09-09
- Owners: PulseGuard maintainers
- Scope: `integrations/mcp`, `.agents/skills/pulseguard-operations`
- Supersedes: none
- Superseded by: none

## Context

Provide AI assistants with project-scoped monitoring and authorized execution through
MCP and a Skill. The existing CLI opens SQLite and creates its own runner; using that
as the AI adapter would duplicate the service's execution capacity and bypass API
project context. The user selected Skill + MCP before a public CLI.

## Decision

- Use the maintained, MIT-licensed official Python MCP SDK for protocol, schemas,
  tool annotations, error results and stdio. Do not implement JSON-RPC manually.
- Package the HTTP adapter separately with uv and its own lockfile; no backend,
  persisted-schema or production dependency change is required.
- Require explicit configured project IDs (or explicit `*`). Require a project ID
  on each scoped tool. Default to read tools; register execution only when enabled
  by startup configuration. No arbitrary URL, arbitrary request or shell tool.
- Reuse existing API execution semantics: current saved definition, formal health
  observation and existing alert policy. Do not simulate a verification mode.
- Treat ambiguous execution responses as unknown and never automatically retry.
  A durable, idempotent submission API is a later service-owned change.
- Restrict screenshot fetches to a PNG path obtained through a project-owned run.
  Bound returned data and reduce sensitive fields. Raw bodies/scripts stay in the console.
- Keep the Skill self-contained and distributable with the repository. It supplies
  domain interpretation and workflows, not authorization enforcement.

## Alternatives considered

- Embed MCP in the FastAPI process: deferred because it changes service lifecycle,
  dependencies and remote authentication obligations for the first release.
- Expose HTTP MCP publicly: deferred until machine authentication, project grants,
  artifact authorization and remote-client requirements are explicitly designed.
- Invoke the existing CLI: rejected because it starts a separate runner and reads
  local persistence instead of sharing the active service execution boundary.
- Add every management endpoint: deferred; configuration writes, secret management,
  upgrades and backups are outside the initial monitoring/execution workflow.

## Consequences

- Positive: AI clients share the existing service's behavior and can use read tools
  without execution tools. The backend image and database are unaffected.
- Negative: installation manages an additional small Python environment. Legacy API
  waits do not provide durable submission IDs, retry idempotency or cancellation proof.
- Security: stdio is a trusted local process. Its allowlist and optional upstream
  gateway credential do not create a backend user authorization system. Free text
  and screenshots can still contain sensitive data.
- Operational: no deployment, live probe or client registration is part of this
  implementation. Stop/remove the configured MCP connection to roll it back; no
  database migration or mixed-version data reader is needed.

## Verification

- Official SDK protocol tests: discovery, input validation, project isolation,
  mutation annotations, output reduction, screenshot paths and unknown outcomes.
- Legacy stdio client against a temporary real backend: success, failure, retained
  runs, failure summary, preceding-success comparison and cross-project rejection.
- Locked dependency check, wheel/source build, and Skill structural validation.
- Existing backend tests use `scripts/test_backend.py` to avoid the instance DB.

## Revisit when

- A client requires remotely hosted MCP, unattended external writes, durable
  execution receipts, bulk submission, cancellation, or separate verification runs.
- A monitored instance outgrows the existing unpaginated task-list API.
