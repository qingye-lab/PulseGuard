# 历史分页的统一筛选索引

- Status: Accepted
- Date: 2026-10-23
- Scope: `/api/runs-page` 全部筛选参数、索引迁移及发布验收

## Context

按类型、运行状态优化的覆盖索引及查询白名单没有覆盖 `notification_status`、节点、分组、触发方式、任务名称等参数。页面显示摘要，但旧计数及筛选会逐条访问包含日志、快照等大字段的 runs 表。用户提供的项目 2 告警发送失败请求再次暴露该问题；线上 EXPLAIN 显示计数使用普通索引，需要回表。

## Decision

用一份完整的轻量筛选索引替换原类型/状态索引。前缀为项目、来源、执行时间和 ID，随后覆盖类型、运行状态、告警状态、节点、分组、触发方式、任务 ID 和任务名称。所有受支持筛选及其组合复用同一 WHERE 条件：精确计数读索引，本页 ID 从索引物化，最后按主键读取最多 page_size 条摘要。日志、快照、响应内容等大字段不进入索引。空结果不重复执行分页扫描。

没有额外筛选时，继续使用同一读快照中的 run_count_totals 精确总数。保留响应结构、精确计数、稳定排序、项目隔离、LIKE 语义、时间边界及 failed 包含 timeout 的既有契约。SQLite 自动维护索引，不引入缓存失效、额外镜像表或双写规则。

迁移版本为 5，列清单与索引结构核对后在事务内替换旧索引；失败回滚旧索引和标记，重复启动不重建正确索引。索引名称及旧查询所需列保留，旧应用源码仍可读取该数据库。发布需要完整恢复点、绑定确切候选清单的数据库副本预演，并在 API/Relay 启动前、写入者停止期间执行兼容迁移。依赖或不兼容格式变更仍须单独流程。

## Alternatives considered

- 为每个字段或字段组合增加索引：组合数量增长，容易再次遗漏，增加写入和存储负担。
- 仅增加告警失败索引：只能修复当前示例，不能解决其他未覆盖筛选。
- 独立摘要表：需要回填、同步和恢复一致性规则；现有索引足以拥有此边界。
- 缓存筛选总数或改成估算总数：会引入失效规则或改变接口契约。
- 直接更换数据库：超出当前单实例模型与已验证问题所需范围。

## Consequences

索引比原类型/状态索引大，新增运行、名称或通知状态更新会维护该索引，但无需逐请求读取大负载。任意名称包含匹配及精确筛选总数仍可能扫描作用域内的轻量索引；本方案不承诺任意数据量、深 OFFSET 或任意主机压力下的常数延迟。

生产验收按全部参数生成单字段与代表性组合，覆盖全部通知状态、运行状态、来源，以及分页边界。副本可显式暂留作独立冷读验证，随后删除；冷缓存驱逐只允许作用于该独立副本，不影响在线数据库或全局页缓存。

## Verification

回归通过 API 签名检查完整筛选参数清单；验证 1,024 种组合的精确总数、稳定跨页结果及覆盖索引计划；覆盖可选作用域、空结果、真实告警参数、字段更新与回滚、旧索引升级和失败迁移回滚。发布另需生产副本迁移、冷读资源采样、真实接口及浏览器验收，实际结果写入当次发布回执。

## Revisit when

筛选或排序契约扩展、名称搜索需要复杂全文语义、数据量或深分页使轻量扫描仍无法满足已明确的延迟目标时，重新评估搜索索引、游标分页或历史分层。
