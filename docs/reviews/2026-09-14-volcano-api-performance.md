## 3. 高优先级发现：分页在返回 12 条数据前统计全部历史

位置：[storage.py:4334](/C:/Users/Qa/Documents/PulseGuard/backend/app/storage.py:4334)、[main.py:1405](/C:/Users/Qa/Documents/PulseGuard/backend/app/main.py:1405)。

当前同一个只读事务内先执行：

```sql
SELECT COUNT(*) FROM runs
WHERE project_id = ? AND observation_kind = ?;
```

随后执行列表查询，排序为 `started_at DESC, id DESC`，再 `LIMIT 12 OFFSET 0/12`。

生产数据实测：

| 部分 | 第 1 页 | 第 2 页 |
| --- | ---: | ---: |
| COUNT | 1090.51 毫秒 | 1094.18 毫秒 |
| 读取 12 条摘要，execute + fetch | 0.31 毫秒 | 0.46 毫秒 |
| 存储函数总时长 | 1092.17 毫秒 | 1096.01 毫秒 |

COUNT 占存储函数耗时超过 99%。当时项目 2 匹配 observation 记录约 134,842 条，项目 1 约 125,522 条，监控运行使数量持续增长。

针对偶发特别慢的补充只读 I/O 实验，读取独立诊断进程的 `/proc/self/io`：

| 查询 | 耗时 | rchar 逻辑读取增量 | read_bytes 磁盘读取增量 |
| --- | ---: | ---: | ---: |
| 仅按 project_id 计数 | 10.64 毫秒 | 约 8.37 MB | 0 |
| project_id + observation_kind 计数 | 1117.83 毫秒 | 约 3.254 GB | 0 |

第二条查询约产生 79.4 万次读调用。这里的 3.254 GB 是系统调用读取字节计数，不是响应体大小、独立数据页大小或本次物理磁盘流量；采样时全部命中系统缓存，仍然耗时超过一秒。相比只走覆盖索引的项目计数，回表访问放大非常明显，说明该路径会对缓存失效和 I/O 竞争敏感。

COUNT 的真实执行计划：

```text
SEARCH runs USING INDEX idx_runs_project_started (project_id=?)
```

该索引只有 `(project_id, started_at DESC)`，不包含 `observation_kind`，因此必须回到 runs 表检查每条候选记录。现有观测类型索引又不含 `project_id`。数据库存在两个单独的访问路径，却没有满足这组联合条件的覆盖索引。

分页列表当前选择 `idx_runs_observation_kind_started`，再检查项目；两页浅分页暂时很快，但它也没有把项目纳入索引前缀。在其他项目数据占比增大时会增加无效遍历。

**建议第一步增加一个联合索引，维持现有精确 total、页码和快照一致性：**

```sql
-- 候选方案：尚未在生产执行
CREATE INDEX idx_runs_project_kind_started
ON runs(project_id, observation_kind, started_at DESC, id DESC);
```

这个索引同时服务计数、项目隔离、观测类型筛选与排序。COUNT 仍然随匹配条数增长，但可以扫描窄索引，消除逐条读取宽记录的成本。不要把精确 total 直接改成估算，也不需要先改变第一页/第二页的分页产品交互。

类型、状态、runner、check 和日期组合应逐一验证真实计划；只为实际慢且高频的组合补索引。深页的 OFFSET 增长问题单独评估，必要时设计游标翻页；它不是本次第 1、2 页约一秒的主因。

- 七天查询返回约 128,030 条记录；逐行读取计时累计约 371.3 毫秒。

- 项目 1 七天返回约 80,932 条，读取约 287.4 毫秒，概览函数约 417.4 毫秒。
- 上述函数诊断为避免主动写入，排除了 `refresh_stale_statuses`；完整 GET 耗时由回环与公网测试另行验证。

查询虽然已经合并为一次七天扫描，仍使用 `(project_id, started_at)` 索引后回表取健康属性、类型、状态、故障类型和耗时。已有 `idx_runs_trend_cover` 缺少 project_id，不能覆盖项目查询。Python 还对成功样本排序计算 24 小时和 7 天的精确 P50/P95。概览在可见时每约 15 秒刷新，会重复支付这些成本。

分两步优化：

1. **先完善项目维度覆盖索引并消除重复调用。** 内存实验验证以下候选能被当前服务器 SQLite 识别为 COVERING INDEX：

   ```sql
   -- 候选方案：尚未在生产执行
   CREATE INDEX idx_runs_project_health_cover
   ON runs(project_id, affects_health, started_at DESC, id DESC,
           check_id, check_type, status, failure_kind, duration_ms);
   ```

   它覆盖今日健康运行计数和七天统计所需字段；最终索引设计还须比较体积、写入增量以及已有索引重叠。部分索引方案也做了实验，但当前 SQLite 的计划未显示为覆盖读取，因此不能只依据索引名称断言“已覆盖”。

2. **再限制重复统计。** 可仅对历史趋势增加按项目、时间窗口、口径版本隔离的短时缓存与同键请求合并，建议最大陈旧时间 15 秒；当前健康状态与即时 stale 判定继续实时获取。15 秒是待实施方案的产品取舍，不是现有行为。恢复数据库、删除项目/历史数据等必须使缓存失效，缓存刷新异常应显式标记陈旧时间并有上限。

如果上述步骤仍达不到目标，再复用现有趋势汇总设施做增量聚合：完整时间桶合并，窗口两端的未对齐区间查原始记录；保持精确 P50/P95 的样本或可精确合并的数据结构。不要平均各桶 P95。

现有 `_run_should_record_trend` 与概览过滤并非完全等价：例如它排除 observation_kind 非 observation 的记录及没有 duration 的成功记录，而概览计数/耗时样本的处理不同。直接改读 trend_rollups 可能悄悄改变成功次数、成功率或分位数。必须先完成口径和窗口边界的逐项对照，再决定复用范围。

## 6. 约 78 秒异常：证据与尚未解决的部分

目前无法将那次 78 秒分配到浏览器排队、传输、服务端排队、数据库等待或执行阶段。

用户补充准确 curl 后的连续采样结果：

| 测试 | 次数 | 中位数 | 最大值 |
| --- | ---: | ---: | ---: |
| 公网同请求头分页 | 30 | 1.137 秒 | 2.159 秒 |
| 同期公网 health | 30 | 24.7 毫秒 | 2.082 秒 |
| 服务器回环分页 | 15 | 1.115 秒 | 1.180 秒 |
| 回环分页期间 health | 40 | 1.8 毫秒 | 315 毫秒 |

连续公网样本全部分页请求都超过一秒；health 有 4 次超过一秒。回环样本没有超过一秒的 health。两组时间段并非严格同时，不能把公网额外延迟完全归因于网络，也不能以公网 health 的 2 秒证明应用事件循环停顿 2 秒。回环 health 的 315 毫秒说明仍值得补充事件循环/线程等待证据。

公网连续测试期间，服务进程逻辑读取累计增加约 97 GB，物理 read_bytes 增量为 0，主机 I/O pressure 接近零；其中绝大多数分页请求稳定约 1.1 秒。上述实验排除了“本次采样时大量物理磁盘读取”这一解释，原 78 秒仍需当时的分段证据。请求头中的 no-cache/Pragma 没有改变服务端每次执行 COUNT 的事实；当前该路径没有响应缓存。

已经确认的事实：

- 访问日志中存在 14:33:11 完成的第 1 页请求，以及 14:36:09 完成的第 2 页请求，路径与用户记录一致。
- 当前日志只含请求完成、路径、HTTP 状态，缺少请求开始与分段耗时；没有 Server-Timing 或等价总耗时中间件。
- 服务在 14:24:43 启动，14:24:46 完成启动。不能把 14:33 的请求认定为应用仍在启动。
- 14:20–14:30 的 sysstat 区间磁盘 await 均值约 40.34 毫秒、队列约 27.51、CPU iowait 约 8.49%；14:30–14:40 区间磁盘 await 降至 1.76 毫秒。系统缓存约从 7.23 GB 降到 4.97 GB，再回到 7.08 GB。
- 这些十分钟粒度数据支持“附近时段存在 I/O 与缓存变化”这一线索，但无法证明 78 秒请求的直接因果。
- 当前反复请求没有复现 78 秒；本轮也未通过清空缓存、重启或压测强行制造生产故障。

最有证据支持的待验证假设是：缺索引导致的大量回表访问，在冷数据/I/O 压力下被放大。数据库维护门、执行线程等待、事件循环阻塞与客户端排队也需要分段计时排查，不能认定为已证实原因。特别是 runs-page 的读路径已避开普通应用写锁，不能泛化为“所有读取被全局写锁串行化”。

建议将可观测性与第一批修复一起交付：

- 请求 ID；服务端总耗时；handler/线程等待；数据库维护门和连接等待；COUNT、列表、趋势 execute/fetch/聚合各段耗时。
- `Server-Timing` 返回关键分段；超过 500 毫秒记慢请求，超过 1 秒全量保留诊断元数据。日志只保存路由模板、状态、项目 ID、阶段耗时与行数，避免请求内容、SQL 敏感参数和凭据。
- 关联事件循环延迟、在途请求、SQLite 写入/提交耗时、磁盘 await/IOPS、WAL 大小。
- 再次出现长等待时保存浏览器 Timing/HAR，与请求 ID 对齐。仅凭 Network 的 Duration 一列不能完成这一判断。

查询 API 可增加明确的执行预算与失败恢复，防止无期限等待；耗时预算应覆盖排队和查询，数据库进度回调/取消要在拥有连接的线程释放事务。浏览器 AbortController 只取消前端等待，不保证服务端 SQL 已经停止。超时兜底不能替代消除慢查询。

## 7. 候选索引实验的适用范围

读取生产库同一只读快照中的约 26 万条运行元数据，复制到独立 `:memory:` SQLite，比较同一批记录加索引前后的查询结果。没有复制日志、请求/响应正文、脚本或密钥，也没有对生产库建索引。

最近一次实验：

| 查询 | 内存元数据基线 | 新索引 | 正确性 |
| --- | ---: | ---: | --- |
| 项目 2 observation COUNT | 69.5–69.6 毫秒 | 首次约 13 毫秒，后两次 5.8–5.9 毫秒 | 134,888，前后一致 |
| 七天趋势读取 | 151–165 毫秒 | 显式覆盖索引 124–134 毫秒 | 128,070 条结果排序后摘要一致 |

COUNT 计划变为覆盖联合索引；趋势计划变为覆盖项目/健康/时间索引。该实验验证方向、执行计划和结果等价；内存元数据表比真实 4 GB 数据库小，索引集合也经过精简，因此不能把这些数字直接当成上线后的端到端时延或索引创建时间。

趋势在内存实验中仍需读取约 12.8 万行，收益显著小于计数。这进一步说明概览要同时减少重复计算，不能仅靠索引保证任意数据量下固定耗时。

| 按证据补充 | 78 秒等待根因修复；只读请求取消和执行预算 | 不再出现无法解释的 >1s 请求；无长期悬挂查询 | Request ID 对齐、取消后资源释放、慢 SQL 与排队分开 |
| 后续 | runners 请求复用、筛选请求防抖/取消；必要时增量趋势聚合 | 减少重复请求和过期结果覆盖 | 网络请求数量、快速筛选/翻页/切项目的真实浏览器验证 |

第一批及第二批核心实现、回归和完整规模验收，粗估 2–3 个工作日；精确增量聚合与历史修复的工作量另行估算，不纳入“加两个索引”的小改动。实际成本取决于数据库副本性能及 78 秒异常是否再次出现。

### PostgreSQL 会改善什么

- 更多并发读写和应用实例：PostgreSQL 的并发控制更适合独立数据库服务；SQLite 的同库单写者机制适合短事务、受控并发。具体收益还取决于是否集中更新同一批趋势行。[SQLite 适用场景](https://www.sqlite.org/whentouse.html)、[PostgreSQL MVCC](https://www.postgresql.org/docs/current/mvcc-intro.html)
- 长期在线历史：按时间分区可以改善有时间条件的访问和批量历史生命周期管理；没有时间条件的精确全历史 COUNT 不能自动靠分区避免扫描。[PostgreSQL 分区](https://www.postgresql.org/docs/current/ddl-partitioning.html)
- 大正文：PostgreSQL TOAST 可以按类型/存储策略对大字段压缩或行外存储，未引用正文的查询有机会少读正文。这是适配当前宽行数据的优势，但不能据此预测提升倍数。[PostgreSQL TOAST](https://www.postgresql.org/docs/current/storage-toast.html)
- 运维能力：可独立规划备份恢复、复制和数据库容量；同时引入连接池、权限、autovacuum、连接数、备份恢复演练等维护责任。

### PostgreSQL 不会自动解决什么

- 精确 COUNT 仍需处理匹配记录的可见性和扫描成本；合适的联合索引仍然必要。[聚合函数说明](https://www.postgresql.org/docs/current/functions-aggregate.html)
- index-only scan 还依赖可见性图；持续更新的页面可能仍需访问 heap，不能假定覆盖索引在所有场景完全免回表。[Index-Only Scans](https://www.postgresql.org/docs/current/indexes-index-only-scans.html)
- 两个接口重复读取 12.8 万行、Python 聚合排序、应用事件循环阻塞不会因连接串变化自动消失。继续把大量行传给 Python，还可能增加数据库到应用的传输成本。
- 已有单机上磁盘仅剩约 7.2 GB，换数据库不会凭空增加容量；同磁盘部署 PostgreSQL 仍会竞争 I/O。

### 决策建议与迁移范围

近期优先实施第 8 节的查询与观测优化，同时明确明细/趋势/外部工件的保留层级。优化后在隔离环境以当前及 3 倍规模、实际写入节奏验证 P95、最大等待、写入提交、清理吞吐和主机 I/O；不要用没有索引的 SQLite 对比有索引的 PostgreSQL 来论证换库收益。

以下任一条件成立时，把 PostgreSQL 纳入确定的实施计划：一年完整明细需要频繁在线检索/分析；应用需要多个实例；实际并发写入和分析争用在合理索引、事务与聚合优化后仍不能满足延迟目标；备份恢复/复制等能力成为服务要求。这些是项目触发条件，不是通用行数阈值。

迁移属于中等规模持久化改造，现有 storage.py 直接使用 sqlite3、SQLite SQL/PRAGMA、快照和备份恢复接口。需要调整数据访问与事务边界、迁移类型和 ID/序列、索引、清理/归档、备份恢复产品流程，并进行旧数据口径对账、切换与回退演练。多应用实例还需要独立处理调度唯一性及进程内维护锁的作用域。不能只替换驱动或连接 URL。

本轮没有部署 PostgreSQL、安装依赖或迁移数据，也没有完成同硬件的 SQLite/PostgreSQL A/B 压测，因此不承诺换库后的具体延迟倍数。
